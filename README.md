# Medical-Triage

Educational classification of English medical abstracts into five medical
categories. This model does not predict clinical urgency and is not intended
for clinical use.

## Reproduce the project

Use Python 3.12, Git, and Docker with Compose. Commands assume the repository
root and a Linux/WSL shell. No GPU is required.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -c constraints.txt -e ".[dev,optimization]"
python -m pip check
```

Obtain `medical_tc_train.csv`, `medical_tc_test.csv`, and `medical_tc_labels.csv`
from the [Medical Abstracts TC Corpus repository](https://github.com/sebischair/Medical-Abstracts-TC-Corpus)
and place them in `data/raw/`. Consult the upstream license and citation before
redistribution; this project's code license does not replace the dataset terms.
Data and generated model binaries are intentionally excluded from Git.

```bash
python scripts/prepare_data.py
python scripts/train_model.py --output models/medical_triage_model.joblib
python -m ruff check src tests scripts
python -m pytest tests/ -q
python -m uvicorn medical_triage.api:app --app-dir src --host 127.0.0.1 --port 8000
```

Open http://127.0.0.1:8000/docs to submit an English abstract to `POST /predict`.
The response contains `condition_label` and `condition_name`; blank text returns
422. Stop Uvicorn with Ctrl+C. Only load trusted joblib artifacts: deserialization
can execute code. Training refuses to overwrite existing models; choose a new
output path for experiments. Data preparation replaces processed CSV files.

## Dataset and modeling decisions

The original 14,438 rows are combined **before creating a new split**. Whitespace
is normalized, texts with conflicting labels are removed, and remaining exact
duplicates are collapsed. This leaves 8,298 texts, split by class into 5,808
training, 1,245 validation, and 1,245 test examples with seed 42. Results therefore
refer to this project's split, not the upstream benchmark split. Cleaning changes
the population; exact deduplication does not guarantee absence of near-duplicates.

Notebooks `01` through `05` cover exploration, preparation, baseline, experiments,
and final evaluation. The selected TF-IDF unigram/bigram model uses `min_df=2`
and balanced Logistic Regression (`C=10`, `max_iter=1000`). The final model fits
train plus validation (7,053 examples). Held-out accuracy is **0.8129**, and macro
F1 is **0.8084**, as recorded in [model metadata](models/model_metadata.json).
The five labels describe neoplasms, digestive, nervous, cardiovascular, and
general pathological conditions—not emergency priority or a diagnosis.

The reusable scripts do not require executing notebooks. Notebook exploration
requires a separate Jupyter environment. `train_model.py` exports a model but
does not regenerate the historical evaluation metadata or benchmark reports.

## Automated training and CI

```bash
docker compose -f compose.airflow.yaml up -d --build
```

Open http://127.0.0.1:8080 and use the credentials generated by Airflow standalone.
If needed, inspect them locally (do not publish them):

```bash
docker compose -f compose.airflow.yaml exec airflow cat /opt/airflow/simple_auth_manager_passwords.json.generated
```

Enable and manually trigger `medical_triage_training`. Its two tasks run data
preparation and training in order. Outputs are isolated by hashed run ID under
`/opt/airflow/training_runs/` in the persistent volume. Trigger a **new run** for
a new model; clearing a successful training task cannot overwrite its artifact.
Training does not automatically promote a model to the API or evaluate the test
set. The standalone installation is for local demonstration only.

```bash
docker compose -f compose.airflow.yaml down
```

[GitHub Actions](.github/workflows/ci.yml) runs lint, tests, a Docker build, and
HTTP smoke checks using a synthetic model. It does not validate real-corpus
quality, publish an image, or deploy a cloud service. Check the actual PR's
Actions status before merging; local success is not remote CI evidence.

## Local monitoring stack

The stack runs the real saved model with FastAPI, Prometheus and a provisioned
Grafana dashboard. Run commands from the repository root.

Prerequisites: Docker with Compose, the project Python environment, and the
trusted local artifact `models/medical_triage_model.joblib` (not tracked in Git).
If the artifact is missing, obtain the original CSV files under `data/raw/` and
run the following commands. Training refuses to overwrite an existing artifact.

```bash
python -m pip install -c constraints.txt -e ".[dev]"
python scripts/prepare_data.py
python scripts/train_model.py --output models/medical_triage_model.joblib
docker compose -f compose.monitoring.yaml up -d --build
```

Stop any older API container occupying port 8001 before starting this stack.
The monitoring Compose uses a separate project name from the Airflow stack.

| Service | Local URL |
| --- | --- |
| API documentation | http://127.0.0.1:8001/docs |
| Metrics | http://127.0.0.1:8001/metrics |
| Prometheus targets | http://127.0.0.1:9090/targets |
| Grafana dashboard | http://127.0.0.1:3000/d/medical-triage-api |

Grafana's initial local login is `admin` / `admin`; change the password when
prompted. The ports bind to loopback only. This configuration is a local demo,
not a hardened public deployment. Grafana provisioning installs the datasource
and dashboard automatically; no manual import is needed.

Generate about one minute of demo traffic:

```bash
python scripts/generate_monitoring_traffic.py
```

One in ten calls intentionally contains blank text and should return 422.
This illustrates client errors; it is not a server failure. The dashboard
separates 4xx and 5xx error percentages. No internal failures are deliberately
generated by this script.

Dashboard panels show prediction request count since process startup, request
rate, p50/p95 processing duration, client/server error percentages, and scrape
availability. Only `/predict` contributes to prediction panels. Health checks
are collected separately, and `/metrics` requests are excluded.

Prometheus scrapes every five seconds. Generate traffic and allow several
scrapes before interpreting rate/percentile panels. With no traffic, latency
percentiles can be empty. Counters reset on API restart. Histogram percentiles
are approximations; durations are server-side, including response-body handling,
and differ from the client's end-to-end benchmark latency.

Metrics contain only bounded method, matched route, and status labels. Unknown
paths use `unmatched`; medical text is never included in metric labels. The
configuration supports a single API worker. Multiple workers/replicas require
additional Prometheus configuration and are not validated here.

```bash
docker compose -f compose.monitoring.yaml ps
docker compose -f compose.monitoring.yaml logs --tail=50 api prometheus grafana
python -m ruff check src tests scripts
python -m pytest tests/ -q
docker compose -f compose.monitoring.yaml down
```

Stopping the stack retains the named volumes. Do not add `--volumes` unless you
intend to delete the monitoring history and Grafana settings. Dashboard JSON
and provisioning YAML are versioned under `monitoring/`.

## ONNX optimization

The selected pipeline is exported without retraining, including TF-IDF and
Logistic Regression. The original joblib artifact remains unchanged and is the
default API backend. ONNX Runtime uses CPU execution with one intra-op and one
inter-op thread. The converter uses locale `C` to avoid dependence on an
unavailable system locale in slim containers.

```bash
python -m pip install -c constraints.txt -e ".[dev,optimization]"
python scripts/export_onnx.py --replace-metadata
docker compose -f compose.monitoring.yaml up -d --build
docker compose -f compose.optimization.yaml up -d --build
python scripts/benchmark_optimization.py --http
```

The exporter always refuses to overwrite an existing ONNX binary. On a fresh
clone, `--replace-metadata` explicitly permits regenerating the tracked JSON
sidecar alongside the missing binary. Review that JSON diff before committing;
historical benchmark hashes may differ from your regenerated artifacts. If both
files already exist, skip export or use `--output` with a new path. Without the
flag, an existing sidecar also blocks export. The default API/Docker configuration
expects `models/medical_triage_model.onnx` and its `.onnx.json` sidecar. Generated
ONNX binaries are ignored by Git; recreate them from the trusted joblib artifact.
The sidecar records label mappings, versions, and source/output SHA-256 hashes.

The optimized API is available at http://127.0.0.1:8002/docs. It is a separate
container and does not replace the original API on port 8001. Its metrics endpoint
is available, but the monitoring dashboard still targets the original API.
For local Uvicorn, set `MODEL_BACKEND=onnx`; omit it to use sklearn.

The benchmark checks all validation/test predictions for conversion fidelity,
then times 100 fixed validation texts across five rounds, with 20 warmups per
backend and alternating backend order. This does not train or tune on the test
set. The validation data was included in final fitting, so its reported quality
is not a generalization estimate. Both HTTP backends are checked against their
local artifacts before timing. Raw timings, versions, hardware context, hashes,
and per-round summaries are in `reports/optimization_benchmark.json`.

| Measurement | sklearn | ONNX |
| --- | ---: | ---: |
| In-process mean latency | 1.236 ms | 0.872 ms |
| HTTP mean latency | 5.591 ms | 4.927 ms |
| HTTP p95 latency | 8.854 ms | 7.542 ms |
| Model file size | 8,243,196 bytes | 6,496,611 bytes |
| Test accuracy | 0.812851 | 0.812851 |
| Test macro F1 | 0.808352 | 0.808568 |

These local observations show approximately 29.5% lower in-process mean latency
and 11.9% lower HTTP mean latency. They are not cloud capacity claims or
statistical guarantees. HTTP measurements include network/serialization overhead;
in-process measurements do not. In-process numerical libraries were restricted
to one thread; the HTTP sklearn service retained its normal container defaults.
Both HTTP services were single-worker, with one outstanding request at a time.

**Conversion is not exactly equivalent:** 4 of 1,245 test labels and 1 of 1,245
validation labels differed. Possible causes include tokenization, casing and
floating-point differences; their individual contributions were not established.
Non-English Unicode equivalence is not guaranteed. The tiny test macro-F1 change
is not evidence of a better trained model. The original remains the default;
ONNX is an explicitly selected optimization candidate for the demonstration.

The old `api_latency_baseline.json` was measured in a different run. Use the new
paired report to assess speedup, not a comparison between different sessions.

```bash
docker compose -f compose.optimization.yaml down
```
